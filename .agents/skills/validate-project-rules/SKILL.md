# プロジェクトルール検証

変更対象に適用されるルールをリポジトリから読み取り、差分の根拠と照合して報告する。ルール本文をこのスキルへ複製せず、常に現在のリポジトリを正とする。

## 監査方針

- 検証のみを依頼された場合はファイルを変更しない。
- 書かれていないルールを推測で追加しない。
- 機械的に判定できる項目と、設計上の判断が必要な項目を分ける。
- 違反を挙げるときは、対象箇所と根拠となるルールファイルを必ず示す。
- 既存の未関連変更を監査対象へ混ぜない。

## 手順

### 1. 対象差分を確定する

ユーザーがファイル、コミット、比較元を指定している場合はそれを優先する。指定がない場合は次の順で対象を決める。

1. staged、unstaged、untracked の変更
2. 作業ツリーがクリーンなら、現在のブランチと `origin/main` の共通祖先からの差分
3. `origin/main` がなければ `main` との差分

最初に次を実行して、対象ファイルとルール候補を収集する。

```bash
python3 .agents/skills/validate-project-rules/scripts/collect_audit_context.py
```

比較元が指定されている場合は `--base <ref>`、staged のみなら `--staged`、ファイル指定なら末尾にパスを渡す。

### 2. 適用ルールを読む

スクリプトが出力した `Rule documents` は候補一覧として扱う。まずルートや変更ファイルの祖先にある `AGENTS.md` / `AGENTS.override.md` を読み、そのルーティング条件に変更内容が合致する参照先だけを順に読む。

そのうえで、各変更ファイルのパスと変更内容に適用されるルールだけをチェックリストへ落とす。ルーターに「特定領域の変更時に読む」とあるルールは、その領域の差分がある場合に適用する。検証・Git・完了条件のような横断ルールは、指定された条件に従って適用する。

`AGENTS.md` が存在しない、または参照先が欠けている場合は、その事実を先に報告する。欠けたルールを補完したつもりで監査を続けない。

### 3. 差分をルールごとに検証する

対象差分を読み、チェックリストの各項目について次を確認する。

- 構造: 責務、依存方向、ファイル配置、コンポーネントや関数の分割
- 実装: import、型、命名、エラー処理、スタイリング、セキュリティ
- 生成物: 自動生成ファイルの扱い、設定やロックファイルとの整合
- 検証: ルールが要求する build、test、lint、型検査、目視確認
- Git: ブランチ、コミット、PR の基点や依存関係

検索結果だけで準拠と断定しない。たとえば `className` の有無は検索できるが、責務の凝集度や I/F の大きさは差分と呼び出し元を読んで判断する。

機械的な検証コマンドは、対象範囲に応じてルールが要求するものを実行する。外部状態の変更、破壊的操作、コミット、push、PR 作成は検証に含めない。実行できない検証は成功扱いにせず、理由を残す。

### 4. 結果を報告する

重大度順に、まず問題点を報告する。

```text
[違反|要確認] 対象ファイル:行 — 要約
根拠: ルールファイル:行
理由: 差分のどの事実が、どの条件に合わないか
対応案: 最小限の修正方針
```

最後に次を簡潔にまとめる。

- 監査した差分範囲
- 適用したルールファイル
- 実行した検証と結果
- 実行できなかった検証と理由
- 問題がなければ「検出した範囲では準拠」と明記し、未実施検証があれば併記

## スクリプト

`scripts/collect_audit_context.py` は監査対象とルール候補の収集、ローカル参照切れの検出、`git diff --check` を担当する。設計ルールの意味的な判定は行わない。
